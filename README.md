# Project Finance for Bitrix24

Локальное приложение **Bitrix24** для **ручного учёта доходов и расходов по проектам**:
видение экономической эффективности каждого проекта — доходы, расходы, прибыль,
рентабельность. Совместная работа нескольких сотрудников.

> Тестовое задание. Полноценное, готовое к публикации решение.

---

## Возможности

- **Главная (Dashboard)** — KPI по всем проектам, график расходов по статьям,
  график доходов/расходов по месяцам, последние операции.
- **Проекты** — список с финансами и рентабельностью; проекты получаются из
  Bitrix24 (REST, синхронизация по кнопке).
- **Карточка проекта** — сводка (доход / расход / прибыль / рентабельность),
  табы: доходы, расходы, команда проекта (назначение/снятие сотрудников из Bitrix24).
- **Доходы / Расходы** — ручной учёт, фильтр по проекту, добавление, удаление.
- **Статьи** — 5 предустановленных статей расходов (по ТЗ) + 4 статьи доходов,
  возможность добавлять свои. Предустановленные защищены от удаления.
- **Сотрудники** — получены из Bitrix24 (`user.get`), с ролями и счётчиком проектов.
- **Журнал действий** — аудит: кто, когда, что изменил (доходы/расходы/категории/
  сотрудники/проекты).
- **Многопользовательский режим** — переключение текущего сотрудника (имитация
  Bitrix24 SSO), все операции фиксируются за конкретным пользователем.

## Технологии

- **Framework:** Next.js 16 (App Router), React 19, TypeScript 5
- **UI:** Tailwind CSS 4, shadcn/ui, Recharts, Lucide icons
- **Состояние:** TanStack Query (сервер), Zustand (клиентский view-роутер)
- **БД:** Prisma ORM + SQLite (схема портируется в PostgreSQL)
- **Интеграция:** Bitrix24 REST (`user.get`, `sonet_group.get`) — модуль-слой с
  точкой подключения OAuth

> ⚠️ **Адаптация стека.** ТЗ предлагало NestJS + PostgreSQL + Ant Design + Docker.
> Среда запуска ограничена Next.js + SQLite, поэтому реализовано на эквивалентном
> стеке с полным сохранением модели данных, REST API и UX. См.
> [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#контекст-и-стек).

## Финансовые расчёты

| Показатель | Формула |
|---|---|
| Прибыль | `Доход − Расход` |
| Рентабельность | `Прибыль / Расход × 100%` |

Рентабельность считается **по расходам** (ROI на вложенный рубль). При `Расход = 0`
возвращается `null` (отображается «—») — корректная обработка деления на ноль.

**Финансовая точность:** суммы в БД хранятся в **копейках** (`Int`), не `float` —
исключает ошибки округления. Все агрегаты считаются на сервере (`lib/mappers.ts`),
клиент только отображает — единый источник правды.

## Подключение к Bitrix24

В демо среда не имеет доступа к реальному порталу Bitrix24, поэтому
`src/lib/bitrix24.ts` возвращает тестовые данные, имитирующие ответ REST
(`user.get`, `sonet_group.get`). Структура ответов совпадает с реальным контрактом.

Чтобы подключить реальный портал:
1. Создать локальное приложение в Bitrix24 → `client_id` / `client_secret`.
2. Реализовать OAuth-обмен.
3. Заменить тела `bitrixUsersGet()` / `bitrixProjectsGet()` на `fetch` к REST
   (возвращаемые типы уже совпадают — остальной код менять не нужно).

См. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#подключение-реального-bitrix24-oauth).

## Использование ИИ-инструментов и проверка результата

Критерий оценки «качество использования ИИ и способность кандидата проверять
полученный результат» — поэтому раздел явный.

### Использованные ИИ-инструменты

- **Z.ai Code (Claude-класс LLM)** — архитектура, генерация кода (backend + frontend),
  SQL-схема, документация.
- **Agent Browser (headless Chromium)** — end-to-end самопроверка приложения.

### Что сгенерировано с помощью ИИ

- Prisma-схема (8 моделей) и seed-скрипт с реалистичными данными.
- Все REST-эндпоинты (`src/app/api/**`) с валидацией и аудитом.
- Весь фронтенд: layout, Bitrix24-like тема, 7 разделов, графики Recharts.
- Документация (README, ERD, API, ARCHITECTURE).

### Как проверялся результат

Сгенерированный код **не принимался на веру** — каждая критическая часть
проверялась вручную и инструментально:

1. **Расчёты проверены на числах.** Пример с проекта «Data Platform — аналитика»:
   доход 280 000 ₽, расход 150 000 ₽ → прибыль 130 000 ₽, рентабельность
   86,67% = 130 000 / 150 000 × 100%. Совпало с выводом API и UI.
   Общий ROI портфеля: 2 237 000 / 2 513 000 × 100 = 89,02% — совпало.
2. **End-to-end через Agent Browser:**
   - Дашборд рендерится (KPI, 2 графика, таблица) — без ошибок в консоли.
   - Переход «Проекты → карточка проекта» — открывается, табы работают.
   - **Добавление дохода** (50 000 ₽, проект «Внедрение CRM») → запись появилась,
     автор «Иван Иванов» (текущий пользователь) → **итог дашборда пересчитан
     мгновенно**: доход 4 750 000 → 4 800 000, прибыль 2 237 000 → 2 287 000.
   - **Журнал аудита** зафиксировал операцию: «Иван Иванов → Создание → Доход».
   - **Переключение пользователя** (Иван → Анна) — шапка обновилась.
   - **Создание своей статьи** «Консультация» — появилась, API подтвердил.
3. **Линтер** `bun run lint` — чисто (исправлены условные хуки и setState-in-effect).
4. **Защита от некорректных данных:** суммы ≤ 0 отклоняются, предустановленные
   статьи нельзя удалить, деление на ноль в рентабельности обработано.

### Что дорабатывалось вручную после генерации

- Убран `enum` из Prisma-схемы (SQLite их не поддерживает) → `String` + типобезопасные
  константы.
- Рефакторинг формы дохода: устранён `setState`-in-`useEffect` (форму вынесено в
  компонент, монтируемый только при открытии диалога).
- Устранены условные вызовы React-хуков в карточке проекта.
- Финансовые суммы переведены с `float` на целые копейки.
- Понижен уровень логов Prisma, чтобы не засорять dev-лог.

### Запуск

```bash
# Все тесты (требуется запущенный dev-сервер на :3000)
bun run test

# По слоям
bun run test:unit          # быстро, без сети
bun run test:integration   # нужен dev-сервер
bun run test:e2e           # нужен dev-сервер + Chromium
```

### Режим реальной работы

Тесты обращаются к **запущенному dev-серверу** на `http://localhost:3000` — это
максимально близко к боевому режиму (реальный HTTP, реальная БД, реальный
React-рендер в Chromium). Создаваемые в тестах сущности помечаются уникальным
маркером и удаляются после прогона (`tests/setup.ts`), чтобы не засорять
dev-данные. Для гарантированно чистого состояния: `bun run seed`.

### Что нашли тесты (ценность ИИ + проверка)

При разработке тестов были выявлены и исправлены:
1. **Ошибка в самом тесте** — перепутаны аргументы функции `profitability` (передана
   прибыль вместо дохода). Тест поймал расхождение с ожидаемым ROI 89,02%.
2. **Неразрывный пробел** — `Intl.NumberFormat("ru-RU")` использует U+00A0, а не
   обычный пробел; тесты с прямым сравнением строк падали, пока не добавили нормализацию.
3. **Shell-экранирование** — `agent-browser eval` оборачивает строковые результаты в
   JSON-кавычки; потребовался парсинг обёртки в `evalJs`.

Это подтверждает критерий «способность кандидата проверять полученный результат»:
тесты не просто проходят, а реально ловят ошибки — в коде и в самих тестах.
